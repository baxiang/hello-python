# 10-测试与部署

> Python 3.11+

本章讲解 FastAPI 应用测试和部署。

---

## 概念铺垫

FastAPI 提供了两种测试方式：`TestClient`（同步，底层基于 `httpx.Client` + `ASGITransport`）和 `AsyncClient`（异步，基于 `httpx.AsyncClient`），两者都**绕过网络层**，直接将请求传递给 ASGI 应用。

```
TestClient.get("/items")
    │
    ▼ 直接调用 ASGI app(scope, receive, send)
    │
    ▼ 收集 send() 调用结果 → 构造 httpx.Response
```

**核心概念：**
- **ASGITransport**：将 HTTP 请求直接传递给 ASGI 应用，不经过 TCP 网络层，测试速度极快（单次 < 1ms）
- **Uvicorn Worker 模型**：主进程 + Worker 进程，每个 Worker 持有独立的事件循环
- **Lifespan**：ASGI 规范的生命周期协议，startup 在 Worker 接受请求前执行，shutdown 在 Worker 退出前执行

**部署架构**：

```
Nginx/Caddy (反向代理)
    │
    ├── Uvicorn Worker 1 (事件循环)
    ├── Uvicorn Worker 2 (事件循环)
    ├── Uvicorn Worker 3 (事件循环)
    └── Uvicorn Worker 4 (事件循环)
```

## 第五部分：完整示例

### 5.1 应用代码

```python
# main.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from typing import Optional

app: FastAPI = FastAPI()


# 模型
class Item(BaseModel):
    id: Optional[int] = None
    name: str
    price: float


# 模拟数据库
items_db: list[Item] = []


# 路由
@app.get("/")
def root() -> dict[str, str]:
    return {"message": "Hello API"}


@app.get("/items", response_model=list[Item])
def get_items() -> list[Item]:
    return items_db


@app.post("/items", response_model=Item, status_code=201)
def create_item(item: Item) -> Item:
    item.id = len(items_db) + 1
    items_db.append(item)
    return item


@app.get("/items/{item_id}", response_model=Item)
def get_item(item_id: int) -> Item:
    for item in items_db:
        if item.id == item_id:
            return item
    raise HTTPException(status_code=404, detail="Item not found")


if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

## 反模式

| ❌ 反模式 | ✅ 改进 |
|-----------|---------|
| 测试之间共享可变状态 | setup/teardown 清理，或使用独立 fixture |
| 只测试 happy path（200），不测错误 | 404、422、401、500 都要覆盖 |
| 测试中硬编码数据库状态 | 每个测试独立创建所需数据 |
| `async def` 端点用 `TestClient` 测试 | 用 `AsyncClient` 避免 loop-in-loop |
| 生产环境 `--reload` 开启 | 生产环境必须关闭 reload |
| Docker 中用 root 用户运行 | `USER 1000` 切换非 root 用户 |
| 不设 `--timeout-graceful-shutdown` | 设置合理值确保请求完成 |

## 何时选用什么

| 需求 | 选用方案 |
|------|---------|
| 同步端点测试 | `TestClient`（API 简洁） |
| 异步端点测试 | `AsyncClient`（共享事件循环） |
| 单机部署 | `uvicorn --workers 4` |
| 多核密集型 | `gunicorn -k uvicorn.workers.UvicornWorker` |
| 容器化 | Docker + uvicorn |
| 开发环境 | `uvicorn --reload` |
| 生产反向代理 | Nginx + Uvicorn Workers |

## 第六部分：L3 专家层

### 6.1 httpx TestClient 的 ASGI 直达（绕过网络层）

`TestClient` 的本质是一个 **同步包装器**，它将 HTTP 请求直接传递给 ASGI 应用，完全绕过网络栈。

**请求流转对比：**

```
# 真实 HTTP 请求
Client ──> TCP ──> HTTP Parser ──> ASGI Server ──> App
         (socket)   (解析协议)      (Uvicorn)

# TestClient 请求
TestClient ──> ASGI Callable ──> App
              (直接调用)
```

TestClient 内部使用 `httpx.Client`，但将其传输层替换为 `ASGITransport`：

```python
# httpx 内部逻辑示意（简化版）
class TestClient(httpx.Client):
    def __init__(self, app: ASGIApp, ...) -> None:
        transport = ASGITransport(app=app)  # ◄── 关键：直达 ASGI
        super().__init__(transport=transport, ...)

    def get(self, url: str, **kwargs) -> Response:
        # 不经过 TCP，直接构造 ASGI scope 并调用 app
        # scope = {"type": "http", "method": "GET", "path": url, ...}
        ...
```

**ASGITransport 的工作方式：**

```
TestClient.get("/items")
     │
     ▼
  构造 ASGI Scope
  ┌──────────────────────────────────┐
  │  type: "http"                    │
  │  method: "GET"                   │
  │  path: "/items"                  │
  │  headers: [(b"host", b"testserver")] │
  │  query_string: b""               │
  └───────────────┬──────────────────┘
                  │
                  ▼
          ┌───────────────┐
          │  app(scope,   │  ◄── 直接调用 ASGI 应用
          │      receive, │
          │      send)    │
          └───────────────┘
                  │
                  ▼
         收集 send() 调用结果
         ┌──────────────────┐
         │ response_start:  │
         │   status: 200    │
         │   headers: ...   │
         │                  │
         │ response_body:   │
         │   body: {...}    │
         └────────┬─────────┘
                  │
                  ▼
          构造 httpx.Response 返回
```

因为没有网络开销，TestClient 的测试速度极快（单次请求 < 1ms），但也意味着它 **无法测试**：
- 网络超时
- 连接池行为
- TLS/SSL 配置
- 真实反向代理的 header 改写

### 6.2 AsyncClient vs TestClient 的区别

| 维度 | TestClient | AsyncClient |
|------|-----------|-------------|
| **API 风格** | 同步（`client.get()`） | 异步（`await client.get()`） |
| **事件循环** | 在测试线程中创建独立循环 | 复用 pytest-asyncio 提供的循环 |
| **底层实现** | `httpx.Client` + `ASGITransport` | `httpx.AsyncClient` + `ASGITransport` |
| **依赖注入** | 支持 | 支持 |
| **websocket 测试** | 支持（`with client.websocket_connect()`） | 支持（`async with client.websocket_connect()`） |
| **适用场景** | 同步测试函数 | `async def` 测试函数 |
| **后台任务** | 在请求结束时同步执行 | 在请求结束时异步执行 |

**核心区别——事件循环的处理：**

```
TestClient（同步）
────────────────────────────────
  测试线程                    新线程
  ┌────────┐               ┌────────┐
  │pytest  │──调用──>      │TestClient│
  │测试函数│               │内部循环  │
  │(同步)  │<──响应──      │await app │
  └────────┘               └────────┘


AsyncClient（异步）
────────────────────────────────
  同一个事件循环
  ┌──────────────────────────────────┐
  │  pytest-asyncio loop             │
  │                                  │
  │  async def test():               │
  │      async with AsyncClient():   │
  │          await client.get("/")   │
  │          └── await app(scope)    │
  └──────────────────────────────────┘
```

**选型建议：**

```
你的 endpoint 是 async def 吗？
    ├── 是 ──> 优先使用 AsyncClient（避免 loop-in-loop 问题）
    │
    └── 否 ──> TestClient 即可

你的测试需要模拟真实异步行为吗？
    ├── 是 ──> AsyncClient
    │
    └── 否 ──> TestClient 更简洁
```

### 6.3 Uvicorn 的 Worker 生命周期

Uvicorn 的进程模型基于 **主进程 + Worker 进程** 架构，理解其生命周期对部署和调试至关重要。

**进程架构：**

```
┌──────────────────────────────────────────────────────┐
│                  Uvicorn Master                       │
│                                                      │
│  ┌─────────────┐                                     │
│  │ 信号处理器   │ ◄── SIGTERM, SIGINT, SIGHUP          │
│  └──────┬──────┘                                     │
│         │                                            │
│  ┌──────▼──────┐   fork/exec    ┌──────────────────┐ │
│  │ Worker 管理器│ ──────────>  │  Worker 1        │ │
│  │             │               │  (事件循环)       │ │
│  │ --workers 4 │   fork/exec    ├──────────────────┤ │
│  │             │ ──────────>  │  Worker 2        │ │
│  │             │               │  (事件循环)       │ │
│  │             │   fork/exec    ├──────────────────┤ │
│  │             │ ──────────>  │  Worker 3        │ │
│  │             │               │  (事件循环)       │ │
│  │             │   fork/exec    ├──────────────────┤ │
│  │             │ ──────────>  │  Worker 4        │ │
│  │             │               │  (事件循环)       │ │
│  └─────────────┘               └──────────────────┘ │
└──────────────────────────────────────────────────────┘
```

**Worker 生命周期状态机：**

```
                    启动
                     │
                     ▼
              ┌─────────────┐
              │  BOOTING    │  ◄── 导入应用、创建事件循环
              └──────┬──────┘
                     │
                     ▼
              ┌─────────────┐
              │  STARTING   │  ◄── 执行 startup lifespan
              └──────┬──────┘
                     │
                     ▼
              ┌─────────────┐
      ┌──────│  RUNNING    │◄──────┐
      │      └──────┬──────┘       │
      │             │              │
      │    处理请求  │              │
      │             │              │
      ▼             ▼              │
┌───────────┐ ┌───────────┐       │
│  GRACEFUL │ │  FORCED   │       │
│  SHUTDOWN │ │  KILL     │       │
│           │ │           │       │
│ 1. 停止   │ │ 立即终止  │       │
│    接受新  │ │           │       │
│    请求   │ │           │       │
│ 2. 等待   │ │           │       │
│    现有   │ │           │       │
│    请求   │ │           │       │
│    完成   │ │           │       │
│ 3. 执行   │ │           │       │
│    shutdown││           │       │
│    lifespan││           │       │
│ 4. 退出   │ │           │       │
└─────┬─────┘ └─────┬─────┘       │
      │             │              │
      └─────────────┴──────────────┘
            进程退出
```

**Lifespan 协议执行时机：**

```python
# FastAPI 应用的 lifespan 上下文
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncGenerator[None, None]:
    # ── STARTUP ──
    # 在 Worker 进入 RUNNING 状态前执行
    await db.connect()
    yield

    # ── SHUTDOWN ──
    # 在 Worker 收到 SIGTERM 后、退出前执行
    await db.disconnect()

app: FastAPI = FastAPI(lifespan=lifespan)
```

**关键生命周期参数：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--timeout-graceful-shutdown` | 15s | 优雅关闭的等待时间，超时后强制终止 |
| `--workers` | 1 | Worker 进程数量 |
| `--reload` | False | 开发模式，文件变更时重启 Worker |
| `--backlog` | 2048 | 等待处理的连接队列大小 |

**优雅关闭的时间线：**

```
T=0s    收到 SIGTERM
        │
        ├── 停止 accept() 新连接
        │
T=0.1s  发送 503 给新请求（如果有）
        │
        ├── 等待现有请求完成
        │
T=2s    请求 A 完成 ✓
T=5s    请求 B 完成 ✓
T=8s    所有请求完成
        │
        ├── 执行 shutdown lifespan
        │
T=8.1s  关闭数据库连接、清理资源
        │
        └── Worker 退出，Master 回收进程
```

如果某个请求超过 `--timeout-graceful-shutdown` 仍未完成，Uvicorn 会强制终止该 Worker，可能导致数据不一致。因此长连接（如 WebSocket、SSE）需要特别处理。

## 常见坑点排查

### 坑点 1：TestClient 测试 async endpoint 的 loop-in-loop 错误

**错误现象**：

```python
# main.py
@app.get("/items")
async def get_items():  # async endpoint
    return await fetch_from_db()

# test_main.py
def test_items():
    client = TestClient(app)
    resp = client.get("/items")  # RuntimeError: This event loop is already running
```

**根因**：`TestClient` 在内部创建了独立的事件循环来运行 async 应用，测试函数本身如果是同步的，会触发嵌套事件循环。

**修复**：

```python
import pytest
from httpx import AsyncClient

@pytest.mark.asyncio
async def test_items():
    async with AsyncClient(app=app, base_url="http://test") as client:
        resp = await client.get("/items")
        assert resp.status_code == 200
```

### 坑点 2：Docker 中 Uvicorn workers 配置错误

**错误现象**：Docker 容器中设置了 `--workers 4`，但实际只有一个进程在运行。

**根因**：容器化环境推荐单 worker + 多容器副本（通过 docker-compose scale 或 k8s replicas），而不是在容器内多 worker。

```
# ❌ 容器内多 worker
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]

# ✅ 单 worker + 多副本
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# docker-compose: deploy.replicas = 4
```

### 坑点 3：测试之间的状态泄漏

**错误现象**：测试 A 通过，测试 B 也通过，但一起跑时 B 失败。

**根因**：`items_db` 在模块级别是可变全局变量，测试 A 修改后影响了测试 B。

**修复**：

```python
import pytest

@pytest.fixture(autouse=True)
def reset_db():
    """每个测试前后自动重置数据库"""
    items_db.clear()
    yield
    items_db.clear()
```

### 坑点 4：健康检查端点返回假阳性

**错误现象**：

```python
@app.get("/health")
def health():
    return {"status": "ok"}  # 永远返回 ok，即使数据库已断开
```

**根因**：健康检查应验证所有关键依赖，而不仅仅是应用进程存活。

**修复**：

```python
@app.get("/health")
async def health():
    checks = {}
    health_status = "ok"

    # 检查数据库
    try:
        async with db_pool.acquire() as conn:
            await conn.execute("SELECT 1")
        checks["database"] = "ok"
    except Exception as e:
        checks["database"] = f"error: {e}"
        health_status = "degraded"

    # 检查 Redis
    try:
        await redis_client.ping()
        checks["redis"] = "ok"
    except Exception as e:
        checks["redis"] = f"error: {e}"
        health_status = "degraded"

    status_code = 200 if health_status == "ok" else 503
    return JSONResponse(
        status_code=status_code,
        content={"status": health_status, "checks": checks},
    )
```

### 坑点排查表

| 现象 | 根因 | 修复 | 预防 |
|------|------|------|------|
| TestClient + async endpoint → RuntimeError | 嵌套事件循环 | 使用 AsyncClient + @pytest.mark.asyncio | 统一异步测试风格 |
| Docker 多 worker 无效 | 容器化不应多 worker | 单 worker + 多副本 | docker-compose scale |
| 测试随机失败 | 共享可变状态 | fixture 隔离 | 每个测试独立创建数据 |
| 健康检查假阳性 | 不检查依赖 | 检查 DB/Redis/外部服务 | 分级：/health、/ready、/live |
| graceful_shutdown 后请求丢失 | timeout 太短 | 增加 --timeout-graceful-shutdown | 监控请求时长 |
| deploy 后旧版本仍在运行 | 无健康检查 | 添加 readiness probe | K8s rolling update |

    return db.get(str(user_id))

    assert resp.json()["name"] == "Test User"

### 7.5 三级健康检查

```python
from fastapi import FastAPI, Response
from fastapi.responses import JSONResponse


@app.get("/health/live")
def liveness() -> dict:
    """存活探针：进程是否运行（K8s liveness probe）"""
    return {"status": "alive"}


@app.get("/health/ready")
async def readiness() -> Response:
    """就绪探针：是否可接受流量（K8s readiness probe）"""
    try:
        # 检查关键依赖
        async with db_pool.acquire() as conn:
            await conn.execute("SELECT 1")
    except Exception:
        return JSONResponse(status_code=503, content={"status": "not ready"})
    return Response(content='{"status":"ready"}', media_type="application/json")


@app.get("/health")
async def health() -> Response:
    """综合健康检查（监控告警用）"""
    checks = {}
    all_ok = True

    # 数据库
    try:
        async with db_pool.acquire() as conn:
            start = time.perf_counter()
            await conn.execute("SELECT 1")
            checks["db"] = {"status": "ok", "latency_ms": round((time.perf_counter() - start) * 1000, 2)}
    except Exception as e:
        checks["db"] = {"status": "error", "message": str(e)}
        all_ok = False

    # Redis
    try:
        start = time.perf_counter()
        await redis.ping()
        checks["redis"] = {"status": "ok", "latency_ms": round((time.perf_counter() - start) * 1000, 2)}
    except Exception as e:
        checks["redis"] = {"status": "error", "message": str(e)}
        all_ok = False

    return JSONResponse(
        status_code=200 if all_ok else 503,
        content={
            "status": "ok" if all_ok else "degraded",
            "version": "2.0.0",
            "uptime": time.time() - START_TIME,
            "checks": checks,
        },
    )
```

### 7.7 Gunicorn + Uvicorn Workers 调优

```bash
# 推荐配置：CPU 密集型应用
gunicorn app.main:app \
  -w 4 \                              # workers = (2 * CPU_CORES) + 1
  -k uvicorn.workers.UvicornWorker \  # ASGI worker 类
  --bind 0.0.0.0:8000 \
  --timeout 30 \                      # 请求超时（秒）
  --graceful-timeout 30 \             # 优雅关闭等待时间
  --keep-alive 5 \                    # Keep-Alive 连接保持时间
  --max-requests 10000 \              # Worker 处理 N 个请求后重启（防内存泄漏）
  --max-requests-jitter 1000 \        # 随机偏移，避免同时重启
  --access-logfile - \                # 访问日志输出到 stdout
  --error-logfile -                   # 错误日志输出到 stderr
  --log-level info
```

**Worker 数量公式**：

| 场景 | Worker 数量 | 原因 |
|------|------------|------|
| I/O 密集型 | 2 × CPU 核心数 | 大部分时间在等待 I/O，多 worker 提升并发 |
| CPU 密集型 | CPU 核心数 | 避免上下文切换开销 |
| 容器化 | 1（多副本） | 通过副本数横向扩展 |
| SSE/WebSocket | CPU 核心数 | 长连接占内存，按需调整 |
