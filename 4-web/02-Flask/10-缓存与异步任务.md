# 10-缓存与异步任务

> Python 3.11+

本章讲解 Flask 缓存机制和 Celery 异步任务。

---

## 概念铺垫

Flask-Caching 提供视图缓存和手动缓存两种模式，支持多种后端（SimpleCache、Redis、Memcached、FileSystem）。Celery 是 Python 异步任务队列，采用三组件架构：Producer（Flask 应用）→ Broker（Redis/RabbitMQ 消息队列）→ Worker（消费者进程）→ Result Backend（Redis/DB 结果存储）。

缓存淘汰策略包括 LRU（最近最少使用）、LFU（最少频率使用）、随机淘汰。Redis 采用近似 LRU 实现。Celery 可靠性由重试机制、ACK Late（任务完成后确认）、死信队列、指数退避+抖动共同保障。

## 第二部分：视图缓存

### 2.1 实际场景

首页文章列表每 5 分钟更新一次，可以缓存视图响应减少数据库压力。

**问题：如何缓存整个视图的响应？**

### 2.2 缓存视图

使用 `@cache.cached` 装饰器缓存整个视图的响应。

```python
from flask_caching import cached
from typing import Any

# 缓存视图 5 分钟
@app.route("/api/articles")
@cached(timeout=300)
def get_articles() -> dict[str, Any]:
    # 模拟耗时操作
    articles: list[Article] = Article.query.all()
    return {"articles": [a.to_dict() for a in articles]}


# 带参数的缓存
@app.route("/api/articles/<int:article_id>")
@cached(timeout=600)
def get_article(article_id: int) -> dict[str, Any]:
    article: Article = Article.query.get_or_404(article_id)
    return article.to_dict()


# 自定义缓存键
@app.route("/api/user/<int:user_id>")
@cached(timeout=300, key_prefix="user_data")
def get_user(user_id: int) -> dict[str, Any]:
    user: User = User.query.get_or_404(user_id)
    return user.to_dict()
```

## 第三部分：数据缓存

### 3.1 实际场景

计算统计数据需要查询大量数据，结果可以缓存一段时间。

**问题：如何手动缓存任意数据？**

### 3.2 手动缓存

使用 `cache.get()` 和 `cache.set()` 手动缓存任意数据。

```python
from flask_caching import Cache
from typing import Any

cache: Cache = Cache()


def get_expensive_data() -> Any:
    """缓存计算结果"""
    # 尝试从缓存获取
    data: Any = cache.get("expensive_data")

    if data is None:
        # 缓存未命中，执行耗时操作
        data = compute_expensive_data()
        # 存入缓存，10 分钟过期
        cache.set("expensive_data", data, timeout=600)

    return data


# 缓存删除
@app.route("/api/cache/clear", methods=["POST"])
def clear_cache() -> dict[str, str]:
    cache.clear()
    return {"message": "缓存已清除"}
```

```python
# celery_app.py
from celery import Celery
from flask import Flask


def make_celery(app: Flask) -> Celery:
    celery: Celery = Celery(
        app.import_name,
        broker=app.config["CELERY_BROKER_URL"],
        backend=app.config["CELERY_RESULT_BACKEND"]
    )

    class ContextTask(celery.Task):
        def __call__(self, *args, **kwargs) -> Any:
            with app.app_context():
                return self.run(*args, **kwargs)

    celery.Task = ContextTask
    return celery
```

### 4.5 任务定义

```python
# tasks.py
from celery import current_task
import time
from typing import Any

celery: Celery = Celery()


@celery.task
def send_email(to: str, subject: str, body: str) -> bool:
    """发送邮件任务"""

    print(f"发送邮件到 {to}: {subject}")

@celery.task
def process_image(image_path: str) -> str:
    """处理图片任务"""
    time.sleep(5)
    return f"处理完成：{image_path}"


@celery.task(bind=True)
def long_running_task(self, data: Any) -> str:
    """带进度追踪的长任务"""
    for i in range(10):
        time.sleep(1)
        # 更新任务状态
        self.update_state(state="PROGRESS", meta={"current": i + 1, "total": 10})
    return "完成"
```

## 第五部分：任务队列使用

### 5.1 实际场景

用户提交邮件发送请求后，立即返回响应，邮件在后台发送。

**问题：如何异步执行任务并追踪状态？**

### 5.2 异步执行任务

```python
from flask import Blueprint, request, jsonify
from typing import Any

api_bp: Blueprint = Blueprint("api", __name__)


@api_bp.route("/api/send-email", methods=["POST"])
def queue_email() -> tuple[dict[str, Any], int]:
    """异步发送邮件"""
    data: dict[str, Any] = request.get_json()

    # 异步执行，立即返回
    task = send_email.delay(
        to=data["to"],
        subject=data["subject"],
        body=data["body"]
    )

    return {
        "message": "邮件已加入队列",
        "task_id": task.id
    }, 202


@api_bp.route("/api/task-status/<task_id>")
def task_status(task_id: str) -> tuple[dict[str, Any], int]:
    """查询任务状态"""
    from celery.result import AsyncResult

    task: AsyncResult = AsyncResult(task_id)

    if task.state == "PENDING":
        response: dict[str, Any] = {"state": task.state, "status": "任务等待执行"}
    elif task.state == "PROGRESS":
        response = {
            "state": task.state,
            "progress": task.info.get("current", 0),
            "total": task.info.get("total", 0)
        }
    elif task.state == "SUCCESS":
        response = {"state": task.state, "result": task.result}
    else:
        response = {"state": task.state, "status": str(task.info)}

    status_code: int = 200 if task.state == "SUCCESS" else 202
    return jsonify(response), status_code
```

### L2 实践层：用好

| 做法 | 原因 | 示例 |
|------|------|------|
| 缓存读多写少的数据 | 减少数据库压力 | 文章列表缓存 5 分钟 |
| 使用 `memoize` 缓存函数结果 | 避免重复计算 | 统计、聚合查询 |
| 异步任务不阻塞请求 | 提升用户体验 | 发邮件、生成报表 |
| 设置任务超时和重试 | 防止僵尸任务堆积 | `time_limit=300, max_retries=3` |
| 不同优先级任务分队列 | 资源隔离 | `-Q high,low` |

#### 反模式

```python
# ❌ 错误：缓存不过期或重试无限
cache.set("data", expensive_result)  # 永久，内存泄漏
@celery.task(max_retries=-1)  # 无限重试浪费资源

# ✅ 正确：设置合理 TTL 和重试上限
cache.set("data", expensive_result, timeout=300)
@celery.task(max_retries=3, default_retry_delay=60)
```

#### 何时缓存 vs 实时查询

| 场景 | 缓存策略 |
|------|---------|
| 文章列表（5 分钟不变） | 5 分钟 TTL |
| 用户个人信息（实时） | 不缓存 |
| 统计看板（1 小时更新） | 1 小时 TTL |
| 配置项（极少变更） | 长期缓存 + 主动失效 |

## 第六部分：L3 专家层

### 6.1 缓存策略：LRU / LFU / 随机

缓存的核心问题是 **淘汰策略** — 当缓存空间满时，决定移除哪些数据。

#### 淘汰算法对比

```
+-------------------------------------------------------------------+
|                        缓存淘汰策略                                 |
+-------------------------------------------------------------------+
|                                                                   |
|  LRU (Least Recently Used)    最近最少使用                         |
|  ┌───┐  ┌───┐  ┌───┐  ┌───┐                                     |
|  | A |->| B |->| C |->| D |  ← 最近访问                           |
|  └───┘  └───┘  └───┘  └───┘                                     |
|   ↑ 淘汰最久未访问的                                                |
|                                                                   |
|  LFU (Least Frequently Used)  最少频率使用                         |
|  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐                          |
|  |A:1次 |  |B:5次  |  |C:3次  |  |D:10次 |                         |
|  └──────┘  └──────┘  └──────┘  └──────┘                          |
|   ↑ 淘汰访问次数最少的                                              |
|                                                                   |
|  Random                      随机淘汰                              |
|  ┌───┐  ┌───┐  ┌───┐  ┌───┐                                     |
|  | A |  | B |  | C |  | D |  → 随机选一个移除                       |
|  └───┘  └───┘  └───┘  └───┘                                     |
|                                                                   |
+-------------------------------------------------------------------+
```

```python
from collections import OrderedDict
from typing import TypeVar, Generic

T = TypeVar("T")

class LRUCache(Generic[T]):
    """基于 OrderedDict 的 LRU 缓存实现"""

    def __init__(self, capacity: int) -> None:
        self._cache: OrderedDict[str, T] = OrderedDict()
        self._capacity: int = capacity

    def get(self, key: str) -> T | None:
        if key not in self._cache:
            return None
        # 访问时移到末尾（最近使用）
        self._cache.move_to_end(key)
        return self._cache[key]

    def put(self, key: str, value: T) -> None:
        if key in self._cache:
            self._cache.move_to_end(key)
        self._cache[key] = value
        if len(self._cache) > self._capacity:
            # 淘汰最久未使用的（队首）
            self._cache.popitem(last=False)
```

#### 性能考量

| 策略 | 查找复杂度 | 插入复杂度 | 淘汰复杂度 | 适用场景 |
|-----|----------|----------|----------|---------|
| LRU | O(1) | O(1) | O(1) | 时间局部性强（最近访问 ≈ 未来访问） |
| LFU | O(1) | O(1) | O(n) 或 O(log n) | 频率局部性强（热点数据长期稳定） |
| Random | O(1) | O(1) | O(1) | 简单场景，无明确访问模式 |

Redis 实际使用 **近似 LRU**（采样少量 key 比较访问时间），以 O(1) 复杂度近似精确 LRU 效果。

#### 设计动机

| 策略选择 | 为什么 |
|---------|-------|
| LRU 最常用 | 实现简单，对大多数 Web 场景效果好 |
| LFU 用于热点 | 防止"扫描污染"（一次性大量访问淘汰掉真正的热点） |
| Random 保底 | 无需维护额外数据结构，内存开销最小 |

### 6.2 Celery 的消息队列架构

Celery 的核心是三组件架构：**Broker → Worker → Result Backend**。

#### 架构图

```
+------------------+     +-------------------+     +---------------------+
|   Flask App      |     |   Message Broker  |     |   Celery Worker     |
|   (Producer)     |     |   (Redis/RabbitMQ)|     |   (Consumer)        |
|                  |     |                   |     |                     |
|  task.delay()    |---->|  ┌─────────────┐  |---->|  worker.process()   |
|  → 消息序列化     |     |  │ Queue: celery│  |     |  反序列化任务        |
|  → 推送到 Broker  |     |  │ - msg_1      │  |     |  执行函数            |
+------------------+     |  │ - msg_2      │  |     |  写回结果            |
                         |  └─────────────┘  |     +----------+----------+
                         +-------------------+                |
                                                              |
                                                    +---------v----------+
                                                    |  Result Backend    |
                                                    |  (Redis/DB/RPC)    |
                                                    |                    |
                                                    |  task_id → result  |
                                                    |  status → SUCCESS  |
                                                    +--------------------+
```

```python
from celery import Celery, Task
from typing import Any

# Broker 负责存储待执行任务的消息
# Result Backend 负责存储任务执行结果
celery_app: Celery = Celery(
    "worker",
    broker="redis://localhost:6379/0",        # 消息队列
    backend="redis://localhost:6379/1",       # 结果存储
)

# 消息体结构（简化）
# {
#   "id": "uuid-xxx",
#   "task": "tasks.send_email",
#   "args": ["user@example.com", "Hello", "Body"],
#   "kwargs": {},
#   "retries": 0,
#   "eta": null,                           # 预计执行时间（定时任务）
#   "expires": null,                       # 过期时间
#   "queue": "celery",                     # 队列名称
# }
```

#### 多队列路由

```python
# 不同任务路由到不同队列

    "tasks.send_email":    {"queue": "email"},
```

#### 设计动机

| 组件 | 为什么分离 |
|-----|----------|
| Broker | 解耦生产者与消费者，提供消息持久化和可靠性 |
| Worker | 独立进程，可水平扩展，失败不影响主应用 |
| Result Backend | 查询结果不需要与 Worker 直接通信 |
| 多队列 | 不同任务优先级和资源需求不同，可独立调度 |

### 6.3 异步任务的可靠性保证

生产环境中，任务可能失败、超时、或 Worker 崩溃。Celery 提供了多层可靠性机制。

#### 可靠性机制

```
+---------------------------------------------------------------+
|                    任务可靠性保障层级                            |
+---------------------------------------------------------------+
|                                                               |
|  1. 重试 (Retry)                                              |
|     ┌──────────┐    fail    ┌──────────┐    fail    ┌───────┐|
|     │ 第1次执行 │───────────>│ 第2次执行 │───────────>│ 第3次 │|
|     └──────────┘  backoff   └──────────┘  backoff   └───┬───┘|
|                                                         |    |
|  2. 死信队列 (Dead Letter Queue)                         |    |
|     超过最大重试次数 ──────────────────────────────────>│    |
|                                                        \|/   |
|                                               ┌──────────────┐|
|                                               │ Dead Letter  │|
|                                               │ Queue        │|
|                                               │ (人工干预)    │|
|                                               └──────────────┘|
|                                                               |
|  3. ACK 机制 (Acknowledgment)                                 |
|     Worker 取走任务 → 执行成功 → 发送 ACK → Broker 删除消息    |
|     Worker 崩溃未 ACK → Broker 重新投递到其他 Worker           |
|                                                               |
+---------------------------------------------------------------+
```

```python
from celery import Celery
from celery.exceptions import Retry
from typing import Any

celery_app: Celery = Celery("worker", broker="redis://localhost:6379/0")

@celery_app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=60,           # 默认重试间隔 60 秒
    acks_late=True,                   # 任务完成后才 ACK（防止 Worker 崩溃丢失）
    reject_on_worker_lost=True,       # Worker 丢失时重新入队
)
def send_notification(self: Task, user_id: int, message: str) -> bool:
    """带可靠性保障的通知发送任务"""
    try:
        result: bool = _send_to_provider(user_id, message)
        return result
    except ConnectionError as exc:
        # 指数退避重试：60s → 120s → 240s
        countdown: int = self.default_retry_delay * (2 ** self.request.retries)
        raise self.retry(exc=exc, countdown=countdown)
    except ValueError as exc:
        # 参数错误不重试，直接失败
        raise exc


@celery_app.task(bind=True, max_retries=5)
def process_payment(self: Task, order_id: str, amount: float) -> dict[str, Any]:
    """支付处理 — 使用指数退避 + 抖动"""
    import random
    try:
        return _execute_payment(order_id, amount)
    except TimeoutError as exc:
        # 指数退避 + 随机抖动（避免重试风暴）
        base_delay: int = 60
        jitter: float = random.uniform(0.5, 1.5)
        countdown: float = base_delay * (2 ** self.request.retries) * jitter
        raise self.retry(exc=exc, countdown=int(countdown))
```

#### 性能考量

| 机制 | 开销 | 效果 | 适用场景 |
|-----|-----|-----|---------|
| 重试 | 额外消息 + Worker 负载 | 临时故障自动恢复 | 网络超时、第三方服务不稳 |
| ACK Late | 消息在队列停留更久 | 防止 Worker 崩溃丢失 | 关键业务（支付、通知） |
| 死信队列 | 需要监控和人工处理 | 失败任务不丢失、可追溯 | 所有生产任务 |
| 指数退避 | 延迟完成 | 避免重试风暴 | 下游服务恢复中 |

#### 设计动机

| 设计 | 解决的问题 |
|-----|-----------|
| `acks_late=True` | 默认 ACK 在任务执行前，Worker 崩溃会导致任务丢失 |
| `reject_on_worker_lost` | 区分"任务失败"和"Worker 崩溃"，后者应重新投递 |
| 死信队列 | 防止无限重试消耗资源，提供人工介入入口 |
| 指数退避 + 抖动 | 防止大量任务同时重试造成下游服务雪崩 |

## 第六部分：Redis 缓存模式实战

### 6.1 实际场景

缓存不只是简单 set/get，不同的业务场景需要不同的缓存策略。

**问题：Redis 缓存有哪些常用模式？各自适用什么场景？**

### 6.2 缓存模式对比

```
┌─────────────────────────────────────────────────────────────┐
│                     Redis 缓存模式                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Cache-Aside（旁路缓存）— 最常用                          │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐            │
│  │  应用     │────>│  缓存    │────>│ 数据库   │            │
│  └──────────┘     └──────────┘     └──────────┘            │
│  读取：先查缓存 → 未命中查数据库 → 写入缓存                   │
│  写入：先写数据库 → 删除/更新缓存                             │
│                                                             │
│  2. Read-Through / Write-Through（穿透读写）                 │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐            │
│  │  应用     │────>│  缓存层   │────>│ 数据库   │            │
│  └──────────┘     └──────────┘     └──────────┘            │
│  应用只与缓存层交互，缓存层自动同步数据库                     │
│                                                             │
│  3. Write-Behind（异步回写）                                 │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐            │
│  │  应用     │────>│  缓存    │ ╌ ╌>│ 数据库   │            │
│  └──────────┘     └──────────┘     └──────────┘            │
│  写入：先写缓存 → 异步批量写入数据库（提高写入吞吐）           │
│  风险：缓存宕机导致数据丢失                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 Cache-Aside 完整实现

```python
import json
import hashlib
from functools import wraps
from flask import request
from flask_caching import Cache
from typing import Any, Callable
import redis

cache = Cache()
r = redis.from_url("redis://localhost:6379")

def cache_aside(
    prefix: str,
    timeout: int = 300,
    serializer: Callable[[Any], str] = json.dumps,
    deserializer: Callable[[str], Any] = json.loads,
):
    """Cache-Aside 模式装饰器"""
    def decorator(f: Callable) -> Callable:
        @wraps(f)
        def wrapper(*args, **kwargs):
            # 构造缓存键
            key_parts = [prefix]
            key_parts.extend(str(a) for a in args)
            key_parts.extend(f"{k}={v}" for k, v in sorted(kwargs.items()))
            cache_key = ":".join(key_parts)

            # Step 1: 读缓存
            cached = r.get(cache_key)
            if cached is not None:
                return deserializer(cached)

            # Step 2: 缓存未命中，读数据库
            result = f(*args, **kwargs)

            # Step 3: 写缓存（加随机 TTL 防雪崩）
            import random
            jitter = random.randint(0, int(timeout * 0.1))
            r.setex(
                cache_key,
                timeout + jitter,
                serializer(result),
            )

            return result
        return wrapper
    return decorator


# 使用
@app.route("/api/articles/<int:article_id>")
@cache_aside("article", timeout=600)
def get_article(article_id: int) -> dict:
    article = Article.query.get_or_404(article_id)
    return article.to_dict()
```

### 6.4 Write-Through 实现

```python
class WriteThroughCache:
    """Write-Through 缓存：写入时同时更新缓存和数据库"""

    def __init__(self, redis_client, db_model) -> None:
        self.r = redis_client
        self.model = db_model

    def get(self, key: str) -> dict | None:
        cached = self.r.get(key)
        if cached:
            return json.loads(cached)
        return None

    def set(self, key: str, data: dict, timeout: int = 300) -> None:
        # 先写数据库
        instance = self.model.query.get(data.get("id"))
        if instance:
            for k, v in data.items():
                setattr(instance, k, v)
            db.session.commit()

        # 再写缓存
        self.r.setex(key, timeout, json.dumps(data))

    def delete(self, key: str, id_value: int) -> None:
        # 先删数据库
        instance = self.model.query.get(id_value)
        if instance:
            db.session.delete(instance)
            db.session.commit()

        # 再删缓存
        self.r.delete(key)

write_through = WriteThroughCache(r, Article)

# 使用场景对比
# Cache-Aside: 读多写少（博客文章、商品信息）
# Write-Through: 读写均衡、需要强一致性（用户配置、库存数量）
# Write-Behind: 写密集、允许短暂不一致（点击统计、浏览记录）
```

```python
    return r.get(versioned_key)

def cache_with_tags(key: str, value: str, tags: list[str], ttl: int) -> None:

    for tag in tags:
        r.sadd(f"tag:{tag}", key)

    """使某个标签下的所有缓存失效"""
    keys = r.smembers(f"tag:{tag}")
    if keys:
        r.delete(*keys)
    r.delete(f"tag:{tag}")

def delete_by_pattern(pattern: str) -> int:
    """使用 SCAN 删除匹配模式的键"""
    cursor = 0
    deleted = 0
    while True:
        cursor, keys = r.scan(cursor, match=pattern, count=100)
        if keys:
            deleted += r.delete(*keys)
        if cursor == 0:
            break
    return deleted
```

### 7.3 缓存穿透、击穿、雪崩

| 问题 | 描述 | 解决方案 |
|------|------|---------|
| 缓存穿透 | 查询不存在的数据，每次都打到数据库 | 布隆过滤器、缓存空值（短 TTL） |
| 缓存击穿 | 热点 key 过期瞬间大量请求打数据库 | 互斥锁（Redis SETNX）、永不过期+异步刷新 |
| 缓存雪崩 | 大量 key 同时过期 | 随机 TTL、多级缓存、限流降级 |

```python
# 防穿透：缓存空值
def get_article_with_null_cache(article_id: int) -> dict | None:
    cache_key = f"article:{article_id}"
    cached = r.get(cache_key)

    if cached is not None:
        if cached == b"__NULL__":
            return None
        return json.loads(cached)

    article = Article.query.get(article_id)
    if article is None:
        r.setex(cache_key, 60, "__NULL__")  # 空值缓存 60 秒
        return None

    r.setex(cache_key, 600, json.dumps(article.to_dict()))
    return article.to_dict()

# 防击穿：互斥锁
import threading

def get_article_with_lock(article_id: int) -> dict | None:
    cache_key = f"article:{article_id}"
    lock_key = f"lock:{article_id}"

    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)

    # 尝试获取锁
    if r.setnx(lock_key, 1):
        try:
            r.expire(lock_key, 10)  # 超时自动释放
            article = Article.query.get(article_id)
            if article:
                r.setex(cache_key, 600, json.dumps(article.to_dict()))
                return article.to_dict()
            return None
        finally:
            r.delete(lock_key)
    else:
        # 等待锁释放后重试
        import time
        time.sleep(0.1)
        return get_article_with_lock(article_id)
```

### 8.4 任务重试高级配置

```python
@celery_app.task(
    bind=True,
    max_retries=5,
    acks_late=True,
    reject_on_worker_lost=True,
)
def call_external_api(self, endpoint: str, payload: dict) -> dict:
    """调用外部 API — 带智能重试"""
    import requests
    import random

    try:
        response = requests.post(
            endpoint,
            json=payload,
            timeout=30,
        )
        response.raise_for_status()
        return response.json()

    except requests.Timeout:
        # 超时：指数退避 + 抖动
        base = 60
        jitter = random.uniform(0.8, 1.2)
        countdown = base * (2 ** self.request.retries) * jitter
        raise self.retry(countdown=int(countdown))

    except requests.HTTPError as e:
        status_code = e.response.status_code if e.response else None

        if status_code and status_code >= 500:
            # 服务端错误：重试
            raise self.retry(exc=e, countdown=30)
        elif status_code == 429:
            # 被限流：使用 Retry-After 头
            retry_after = int(
                e.response.headers.get("Retry-After", 60)
            )
            raise self.retry(exc=e, countdown=retry_after)
        elif status_code and 400 <= status_code < 500:
            # 客户端错误：不重试
            raise e
```

## 第十部分：Flask-Caching 深入

### 10.1 memoize 装饰器解析

`@cache.memoize` 与 `@cache.cached` 的核心区别：memoize 根据函数参数生成缓存键，cached 使用固定键或基于 URL 的参数。

```python
from flask_caching import Cache

cache = Cache()

# cached: 基于显式或默认 key_prefix
@cache.cached(timeout=300, key_prefix="articles")
def get_articles():
    return Article.query.all()

# memoize: 基于函数参数自动生成缓存键
@cache.memoize(timeout=300)
def get_user_articles(user_id: int, category: str = "all"):
    return Article.query.filter_by(author_id=user_id, category=category).all()

# get_user_articles(1, "tech") 和 get_user_articles(1, "life") 是不同缓存
# get_user_articles(2, "tech") 是另一个不同的缓存

# 精确删除 memoize 缓存
cache.delete_memoized(get_user_articles, 1, "tech")  # 删除特定参数的缓存
cache.delete_memoized(get_user_articles)             # 删除所有参数的缓存
```

### 10.2 自定义缓存键生成

```python
from flask import request, g

def make_cache_key(*args, **kwargs) -> str:
    """基于用户角色 + URL + 参数生成缓存键"""
    user_role = getattr(g, "user_role", "anonymous")
    path = request.path
    query = request.query_string.decode() or ""
    return f"{user_role}:{path}:{query}"

@app.route("/api/articles")
@cache.cached(timeout=300, key_prefix=make_cache_key)
def articles():
    # 不同角色的用户看到不同内容，缓存键不同
    articles = Article.query.filter_by(
        visible_to=getattr(g, "user_role", "anonymous")
    ).all()
    return {"articles": [a.to_dict() for a in articles]}
```

### 11.3 问题排查表

| 现象 | 可能原因 | 检查方法 | 解决方案 |
|------|---------|---------|---------|

```python
def benchmark_cache_operations(num_ops: int = 10000) -> None:
    r = redis.from_url("redis://localhost:6379")
    test_key = "benchmark:test"
    test_value = json.dumps({"data": "x" * 1024})  # 1KB

    # SET
    start = time.perf_counter()
    for _ in range(num_ops):
        r.setex(f"{test_key}:{_}", 60, test_value)
    set_ops = num_ops / (time.perf_counter() - start)

    # GET
    keys = [f"{test_key}:{i}" for i in random.sample(range(num_ops), min(1000, num_ops))]
    start = time.perf_counter()
    for key in keys:
        r.get(key)
    get_ops = len(keys) / (time.perf_counter() - start)

    # PIPELINE SET
    start = time.perf_counter()
    pipe = r.pipeline()
    for _ in range(num_ops):
        pipe.setex(f"{test_key}:pipe:{_}", 60, test_value)
    pipe.execute()
    pipe_ops = num_ops / (time.perf_counter() - start)

    print(f"SET:       {set_ops:.0f} ops/s")
    print(f"GET:       {get_ops:.0f} ops/s")
    print(f"PIPELINE:  {pipe_ops:.0f} ops/s")

    # 清理
    for _ in range(num_ops):
        r.delete(f"{test_key}:{_}", f"{test_key}:pipe:{_}")
```

### 13.2 缓存命中率监控

```python
class CacheMetrics:
    """缓存命中率统计"""

    def __init__(self, redis_client) -> None:
        self.r = redis_client
        self.metrics_key = "cache:metrics"

    def record_hit(self) -> None:
        self.r.hincrby(self.metrics_key, "hits", 1)

    def record_miss(self) -> None:
        self.r.hincrby(self.metrics_key, "misses", 1)

    def record_set(self) -> None:
        self.r.hincrby(self.metrics_key, "sets", 1)

    def record_eviction(self) -> None:
        self.r.hincrby(self.metrics_key, "evictions", 1)

    def get_hit_rate(self) -> float:
        hits = int(self.r.hget(self.metrics_key, "hits") or 0)
        misses = int(self.r.hget(self.metrics_key, "misses") or 0)
        total = hits + misses
        return hits / total if total > 0 else 0.0

    def get_summary(self) -> dict:
        return {
            "hits": int(self.r.hget(self.metrics_key, "hits") or 0),
            "misses": int(self.r.hget(self.metrics_key, "misses") or 0),
            "sets": int(self.r.hget(self.metrics_key, "sets") or 0),
            "hit_rate": f"{self.get_hit_rate():.2%}",
        }


# Flask 端点暴露缓存指标
@app.route("/api/cache-metrics")
def cache_metrics():
    metrics = CacheMetrics(r)
    return metrics.get_summary()
```
